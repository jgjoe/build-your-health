# V2 성능 후속 — 혼합 API 처리 한계의 원인 분리와 개선

V1 기록(`docs/load-test.md` §8, 2026-10-06 KST)에서 관측했지만 원인을 분리하지 못한 320 TPS 실패를 재현하고, 원인을 통제 실험으로 나눈 뒤, 개선 하나를 같은 조건에서 전후 비교한다. 로컬 Docker 단일 환경이며 운영 트래픽이 아니다.

## 0. 역할 구분

| 누가 | 한 일 |
|---|---|
| AI 코딩 에이전트 | 하네스·분석기·앱 코드 작성, 측정 실행, 원자료 집계, 문서 초안 |
| 본인(지관) | 단계별 계획 승인, 측정 기준·가설 답변, 결과 해석·채택 판단 |

## 1. 1단계 — 재현과 한계 지점

### 1.1 측정 전 설계 (2026-10-19 KST 승인)

- 조건: V1 §8과 같다. Docker VM 4 CPU, 앱 2 CPU·2GiB(heap 512MiB~1GiB), Oracle Free(CPU_COUNT=2), 고정 시드(회원 22,021·상품 2,001·주문 600,000·주문상품 1,499,546), 혼합 상품 70%(검색 10%p 포함)·주문 내역 15%·로그인 10%·주문 생성 5%, constant-arrival-rate, 256 VU, HTTP timeout 5초, 단계마다 30초 워밍업·10초 간격·120초 측정 2회.
- 앱 JAR SHA256 `b295004e1e49691a1a7b0cd0a7fec1daaea0cffca7e5541619d603efe7df4dad`, 이미지 `sha256:9d7ce99ad1bf…`가 V1과 같음을 확인했다(`remake/loadtest/results/v2-environment/`). 시작 시 원본/복제 콘텐츠 해시 4종이 V1 결과와 같다.
- 하네스 변경: `Staircase.ps1`에 `-Stages` 파라미터만 추가(기본값은 기존 목록). `capacity.js`, `Run-Capacity.ps1`, `CapacityProbe.java`, 분석기는 바꾸지 않는다. 포화 시 JMX 표본이 성겨지는 한계도 비교 가능성을 위해 그대로 둔다.
- 중단 기준(V1과 같음): 혼합 p95 >500ms, 업무 오류율 ≥1%, warmup/measured drop >0.
- 1-A 재현(label `v2-repro`): 160, 320 TPS 각 2회.
- 1-B 세분화(label `v2-step`): 200/240/280 TPS 각 2회로 구간을 찾고, 마지막 통과~첫 실패 구간을 10 TPS 간격 각 2회로 좁힌다.

### 1.2 측정 전 확정한 판정 기준

- 재현 판정: 160 TPS p95가 V1 73.52~76.20ms의 ±25% 안, 320 TPS 정상 응답 처리량이 V1 210.89~217.34 TPS의 ±10% 안, 오류가 로그인에 집중, 앱 CPU 2.00코어.
- 한계의 정의: 두 회차 모두 중단 기준을 통과한 최고 TPS. 마지막 통과·첫 실패 구간을 10 TPS 해상도로 함께 적는다.

### 1.3 재현 결과 (2026-10-19 KST)

첫 시도(label `v2-repro`)는 160 TPS 2회차가 측정 97초까지 정상(초당 약 160건, 최대 72ms, 앱 1.13코어, CPU 제한 0회)이다가 98초에 앱·Oracle·k6 CPU가 동시에 튀고 관측 표본 간격이 6~14초로 벌어진 뒤, 실행 HTTP 스레드 104개·BCrypt 프레임 스레드 90개까지 쌓여 측정 끝까지 회복하지 못했다(p95 1,716.97ms, 오류 1.064% 중 로그인 196건, drop 501). 앱 내부 변화의 흔적은 없고 VM 단위 교란이 계기였을 가능성이 높으나, VM·호스트 CPU를 수집하지 않아 **계기는 확정하지 못했다.** 이 회차는 "일시 교란 후 회복하지 못하는 붕괴" 사례로 보존한다.

## 2. 원인 분리

### 2.1 측정 전 설계 (2026-10-19 KST, 측정 전 작성)

앱 코드는 바꾸지 않고 하네스와 환경 변수만 바꾼다. 바꾼 항목의 기본값은 1단계와 같다.

- `capacity.js`의 `MIX`: `mixed`(기본, 20칸 혼합), `login`(로그인만), `nologin`(혼합 주기에서 로그인 2칸을 뺀 18칸, 나머지 비율 유지).
- `compose.yaml`의 `POOL_SIZE`(Hikari 최대 풀, 기본 10 = Spring Boot 기본값)와 `JFR_OPTS`. `Restart-App.ps1`이 같은 이미지로 앱 컨테이너를 다시 만들고, 실행 설정은 회차마다 `app-config.txt`에 남긴다.
- JFR: `settings=profile` 기록을 JVM 종료 시 덤프하고(`Collect-Jfr.ps1`), `analyze_jfr.py`가 측정 120초 구간의 `jdk.ExecutionSample`을 분류한다. 이 표본은 Java 코드를 실행 중인 스레드만 잡으므로 Java CPU 시간 비율의 근사이며, GC·JIT·네이티브 시간은 포함하지 않는다.
- 일괄 실행: `Run-V2Isolation.ps1`. 모든 실험은 새로 기동한 앱에서 시작한다. 1단계 회차(장시간 기동된 앱)와의 차이는 30초 워밍업으로 흡수한다고 가정하고, 풀 크기 비교는 풀 10도 같은 방식으로 다시 측정한다.

| 실험 | 조건 | 가설 | 판정에 쓰는 지표 |
|---|---|---|---|
| E1 로그인만 | 20→25→30→35→40 TPS, 각 2회, 중단 기준 동일 | 한계 약 30 TPS(1회 약 65ms CPU × 30 ≈ 2코어) | 한계 TPS, 로그인 1건당 앱 CPU 시간 |
| E2 로그인 제외 혼합 | 243(270의 90%)→480→960 TPS, 각 2회 | 243에서 앱 CPU 0.3코어 이하, 한계는 수백 TPS 이상 | 1건당 CPU 시간, 한계 TPS |
| E3 풀 크기 | 풀 5·10·20 × 혼합 270·300 TPS × 2회, 계단 중단 없이 전부 측정 | 한계·지연이 풀 크기에 거의 무관. 풀 20은 꼬리 지연이 오히려 늘 수 있음 | p95·p99·drop, Hikari awaiting, CPU |
| E4 JFR | 풀 10 × 혼합 270·300 TPS, 각 1회 | Java 실행 표본의 약 85~95%가 BCrypt | 범주별 표본 비율 |

기여도는 E1·E2의 요청 1건당 CPU 시간과 E4의 표본 비율로 계산한다. 1단계의 "BCrypt 스택 표본 비율"(실행 중 HTTP 스레드 스택에 BCrypt 프레임이 있는 비율)은 CPU 점유율이 아니므로 기여도에 쓰지 않는다. Hikari 대기가 원인인지 CPU 포화의 결과인지는 E3로 판정한다. 로그인 하한 20 TPS는 하네스의 최소 도착률 검사(20)를 그대로 둔 결과다.

풀을 키우면 Hikari 대기는 줄지만 300 TPS 오류율은 오히려 늘었다(풀 20이 풀 5의 약 5배). 대기 대신 동시 실행 스레드가 늘어 같은 2코어를 더 잘게 나눠 쓰기 때문으로 해석한다. 270 r2의 p99 차이는 풀 10·20 회차의 측정 첫 30초 지연(아래)에서 나왔다. 풀 5 회차에는 이 구간이 없었지만 풀마다 통과 회차가 하나뿐이라 풀 크기 효과로 판정하지 않는다. Hikari 대기는 원인이 아니라 CPU 포화의 결과다.

**예상 밖 결과: 기동 직후에는 270 TPS를 버티지 못한다.** 새로 기동한 앱의 첫 회차는 풀 크기와 JFR 여부에 관계없이 270 TPS에서 4번 모두 실패했고, 같은 JVM의 두 번째 회차는 3번 모두 통과했다. 실패 회차는 CPU 제한 기간이 100%였고 p95가 측정 내내 회복되지 않았다(풀 10: 10초 구간 p95가 884ms에서 3,009ms로 증가). 통과 회차 중 풀 10·20은 첫 30초 p95가 339~604ms였다가 이후 60~68ms로 안정됐고, 풀 5는 처음부터 62~69ms였다. 1단계는 오래 기동된 앱에서 측정했다. 로그인 1건이 지연 없이 처리되려면 JIT 컴파일이 끝나야 하는데, 여유가 8%뿐인 270 TPS에서는 컴파일 중에 쌓인 대기열을 해소할 CPU가 부족했다고 추정한다(JIT 로그로 확인하지 않음). 따라서 V2 한계 270 TPS는 **충분히 워밍업된 JVM에서만** 성립한다. 3단계 전후 비교는 기동 직후와 워밍업 후 두 상태를 같은 절차로 각각 측정한다.

가설 대조:

| 실험 | 가설 | 결과 |
|---|---|---|
| E1 | 한계 약 30 TPS | 맞음(30 통과, 35 실패) |
| E2 | 243에서 0.3코어 이하, 한계 수백 TPS 이상 | 맞음(0.18코어, 960까지 통과) |
| E3 | 한계가 풀 크기와 무관, 풀 20은 꼬리 지연 증가 가능 | 한계 무관은 맞음. 악화는 꼬리 지연이 아니라 300 TPS 오류율로 나타남 |
| E4 | BCrypt 85~95% | 상단(94.6~95.4%). CPU 비용 기준으로는 약 90% |
| - | (가설 없음) | 기동 직후 270 TPS 실패 |

결론: V2 처리 한계는 로그인 BCrypt의 CPU 비용 하나로 거의 설명된다. 커넥션 풀은 병목이 아니고, 풀 확대는 과부하 시 오류를 늘린다. 개선은 로그인 1건의 CPU 비용 또는 로그인 처리 방식을 다뤄야 하며, BCrypt 강도를 낮추는 방식은 쓰지 않는다.

## 3. 개선: 로그인 동시 처리 제한과 기동 시 예열

### 3.1 측정 전 설계 (2026-10-20 KST, 측정 전 작성)

목표는 로그인 처리량을 늘리는 것이 아니다. BCrypt cost 10을 유지하면 2코어의 로그인 처리량은 초당 약 30건으로 고정된다. 목표는 두 가지다. 로그인이 몰려도 다른 API가 기준 안에 머물게 하고 로그인은 타임아웃 대신 즉시 거절되게 하는 것, 그리고 기동 직후 붕괴를 없애는 것이다.

변경(앱):

- `LoginGate`: `Semaphore`로 동시 로그인 수를 제한한다(`byh.login.max-concurrent`, 기본 2). 한도를 넘으면 기다리지 않고 즉시 429, 코드 `TOO_MANY_REQUESTS`, `Retry-After: 1`로 응답한다. 거절은 회원 조회 전에 일어나므로 DB·BCrypt 작업과 세션 변경이 없다. 입력 검사(400)는 제한보다 먼저 한다.
- `PasswordWarmup`: 컨텍스트 초기화 중, 내장 서버가 요청을 받기 전에 임시 비밀번호로 BCrypt 검사를 N번 실행한다(`byh.login.warmup-iterations`, 기본 20). 기본값 20은 가정이며 측정으로 판단한다.
- 테스트(`mvnw verify`, CI): 동시 실행 상한, 거절 시 로그인 작업 미실행, 예외 후 허가 반납, 과다 반납 없음, 잘못된 설정값 거부, 거절 시 SQL 0건·세션 불변·429 계약, 예열 호출 횟수, 새 해시의 `$2a$10$` 접두사와 맞음/틀림 판정. 통합 테스트 컨텍스트는 모두 예열을 켠 기본값으로 기동한다.

하네스: 로그인 결과를 `ok`(200), `rejected`(429 + 코드 + `Retry-After`), `error`(그 밖)로 나눈다. `measured_errors`는 `error`만 센다. 거절은 성공으로 세지 않는다. 분석은 로그인 성공률(성공 ÷ 시작), 거절 지연, 로그인 외 API별·전체 지연과 오류, setup·워밍업을 포함한 10초 구간 타임라인, 앱 기동 시간과 예열 시간을 기록한다. 회차마다 이미지 ID와 설정을 `app-config.txt`에 남긴다.

설정과 순서(`Run-V2Stage3.ps1`):

| 설정 | 이미지 | 동시 로그인 | 예열 |
|---|---|---|---|
| before | 기존 이미지 `byh-loadtest-app:latest`(1·2단계와 같은 JAR) | 제한 없음 | 없음 |

판정 기준(설정마다 2회 모두 충족해야 통과):

| 기준 | 조건 | 판정 |
|---|---|---|
| P1 과부하 보호 | 워밍업 후 320·400 TPS | 상품·주문 내역·주문 생성 각각 p95 < 500ms, 로그인 외 오류 0건, drop 0. 로그인은 `ok`·`rejected`만(예상 밖 오류·미완료 0), 거절 p95 < 100ms |

가설: before는 P1(320·400)과 P3에서 실패한다. a1은 270 TPS 로그인 수요(초당 27건)가 한도(초당 약 16건)를 넘어 P2에서 실패한다(성공률 약 60%). a2는 P1·P2를 통과한다. 로그인이 최대 2코어를 쓸 수 있어 cgroup 제한은 걸리지만 로그인 외 p95는 200ms 아래라고 본다. 기동 직후는 제한만으로도 대기열이 쌓이지 않아 a2nowarm도 통과할 수 있다. 그렇다면 예열의 효과는 기동 직후 첫 구간의 지연에서만 보인다.

범위 밖: 계정별 로그인 시도 제한(무차별 대입 방어)과 BCrypt 강도 변경. 별도 과제: 없는 아이디는 BCrypt 검사를 건너뛰어 응답이 빠르므로, 응답 시간으로 계정 존재 여부를 추측할 수 있다.

해석:

- **과부하 보호는 동작한다.** before는 320·400 TPS에서 CPU가 2코어에 고정되고(cgroup 제한 기간 약 100%) 로그인 외 API p95가 610~874ms로 올라갔다. 로그인은 5초 타임아웃으로 1065~2853건 실패했다. a2는 같은 부하에서 로그인 외 p95가 15ms 이하이고 예상 밖 오류는 0건이다. 넘친 로그인은 p95 5ms 이하로 즉시 거절됐다. 400 TPS에서 성공한 로그인은 a2가 초당 약 20건, before가 약 6~8건이다. 제한이 없으면 모든 로그인이 CPU를 나눠 쓰다 함께 타임아웃되기 때문이다.
- **a2 400 TPS 2회차 drop 767건**은 측정 구간이 아닌 k6 워밍업 구간에서 났다. 같은 시점에 호스트 CPU p95가 84%였다(Chrome, 측정을 돌린 에이전트 앱). 같은 설정 400 TPS 1회차의 호스트 CPU p95는 39%였다. 외부 교란으로 추정하지만 확정할 수 없으므로 판정은 실패로 둔다.
- **99% 미달 원인(추정).** a2는 270 TPS에서 로그인 수요(초당 27건)가 로그인만 보낼 때의 한계(초당 약 30건, 2단계)의 90%다. 한도에 도달하면 기다리지 않고 바로 거절하므로, 도착이 순간적으로 겹칠 때마다 거절이 난다(약 2.6%). 3.1절에서 "거절은 기다리지 않는다"로 정한 설계와 "정상 부하 성공률 99%"가 이 부하에서는 함께 성립하지 않았다. 대기열 길이로 직접 확인하지는 않았다.
- **a1은 가설보다 처리량이 낮았다.** 초당 약 16건을 예상했지만 실제 성공은 초당 약 13.5건(270 TPS)이었다. 로그인 1건이 끝난 뒤 다음 허가가 나기까지 생기는 빈틈이 처리량을 깎은 것으로 보인다.
- **기동 직후 붕괴는 제한만으로 사라졌다.** before 기동 직후 회차는 k6 워밍업 구간 10초 단위 p95가 2.5~3.9초였고, setup·워밍업 중 오류가 8~12건, 측정 구간 drop이 544~985건이었다. a2와 a2nowarm은 첫 10초부터 p95 95ms 이하, 오류 0건이었다. 예열 유무에 따른 차이는 측정되지 않았다(a2nowarm 성공률이 오히려 약 1%p 높다). 예열은 기동 시간을 약 1.3~1.4초 늘렸다(3.3~3.8초 → 4.9~5.2초). 가설대로 대기열이 쌓이지 않으면 JIT가 끝나기 전에도 무너지지 않았다.
- **BCrypt 비용은 그대로다.** 로그인만 20 TPS에서 성공 1건당 CPU는 before 62.5ms, a2 61.5ms다. 새 해시가 강도 10(`$2a$10$`)인지는 단위 테스트로 확인했다.

결론(3.2 시점): 동시 로그인 제한은 과부하 때 다른 API를 지키고 기동 직후 붕괴를 없앴다. 그러나 즉시 거절 방식은 정상 부하(270 TPS)에서 로그인을 약 2.6% 거절해 측정 전에 정한 99% 기준을 넘지 못했다. 기동 시 예열은 효과가 측정되지 않았다.

### 3.3 후속: 짧은 대기와 예열 제거 (2026-10-20 KST, 측정 전 작성)

변경(앱):

- `LoginGate`: 허가가 없으면 즉시 거절하지 않고 최대 `byh.login.max-wait-ms`(기본 50ms) 기다린 뒤 거절한다. 대기 중 인터럽트되면 인터럽트 상태를 복원하고 거절한다. 음수 설정은 기동 시 거부한다. 50ms는 로그인 1건 처리 시간(약 62~70ms)보다 짧아서, 앞선 로그인이 끝나 가는 동안 도착한 요청을 받아 줄 수 있으면서 거절 응답은 100ms 기준 안에 둔다.
- `PasswordWarmup` 삭제: 3.2에서 효과가 측정되지 않았고 기동 시간만 늘렸다. BCrypt 강도 테스트는 `PasswordConfigTest`로 옮겼다.
- 테스트: 한도 도달 시 대기 후 거절(대기 시간 확인, 작업 미실행), 대기 중 허가 반납 시 입장, 인터럽트 시 거절과 플래그 복원, 음수 대기 거부. 통합 테스트(`LoginRejectionTest`)는 기본값 50ms 대기 후 429를 확인한다.

측정(`Run-V2Stage3b.ps1`): 새 이미지 `byh-loadtest-app:stage3b`, 동시 로그인 2, 예열 없음. 대기만 다르게 둔다: wait50(50ms)과 wait0(즉시 거절, 3.2 a2nowarm과 같은 동작). 세션마다 새 JVM으로 기동 직후 270 TPS를 재고, 이어서 워밍업 후 270·320·400 TPS를 잰다. 세션 순서는 wait50, wait0, wait0, wait50(대칭). 합계 16회.

판정: 3.1의 P1·P2·P3 기준을 그대로 쓴다(P2·P3 로그인 성공률 99% 이상, 거절 p95 100ms 미만 포함). 기준은 바꾸지 않는다. wait50이 2회 모두 P1·P2·P3을 통과하면 기본값(동시 2, 대기 50ms)으로 채택한다. 통과하지 못하면 그 사실을 기록하고 기본값은 채택하지 않는다.

가설: wait50은 270 TPS 성공률이 99% 이상이 된다. 거절은 대부분 순간적인 겹침 때문이라 50ms 안에 허가가 풀린다고 본다. 과부하(320·400)에서는 거절 p95가 약 50ms로 늘지만 100ms 미만이고, 로그인 외 p95와 오류는 wait0과 같은 수준이다. 성공한 로그인 p95는 대기만큼(최대 50ms) 늘어난다. wait0은 3.2 a2nowarm처럼 성공률 약 97.4%로 재현된다.

**P3을 넘지 못했으므로 3.3의 규칙대로 기본값으로 채택하지 않는다.** 코드 기본값(동시 2, 대기 50ms)은 측정한 설정 중 기준에 가장 가까운 값으로 남겨 두며, 판정으로 채택된 값은 아니다.

해석:

- **짧은 대기가 정상 부하의 거절을 거의 없앴다.** 워밍업 후 270 TPS 거절은 wait0이 83~106건, wait50이 1~2건이다. 3.2에서 추정한 원인(순간적인 겹침)과 맞는다. wait0은 3.2 a2nowarm의 결과(약 97.4%)를 재현했다.
- **과부하에서는 성공한 로그인이 늘었다.** 400 TPS에서 성공한 로그인은 wait50이 초당 약 29건, wait0이 약 20건이다. 대기 덕분에 허가가 비는 틈이 줄어 로그인 처리 능력(초당 약 30건, 2단계)에 가까워졌다. 그 대가로 CPU 제한 기간이 약 90%로 늘었지만(wait0은 0.4~13%), 로그인 외 p95는 17ms 이하로 유지됐다. 성공 로그인 p95는 대기만큼 늘었다(약 75ms에서 약 125ms).
- **기동 직후에만 미달이다.** 기동 직후 회차의 성공 로그인 p95는 104~107ms로 워밍업 후(76~79ms)보다 길다. 로그인이 느린 동안 대기 50ms 안에 허가가 풀리지 않아 거절이 남은 것으로 추정한다. 거절은 측정 구간 전체에 퍼져 있었다. 이 두 회차의 호스트 CPU p95는 68~73%로, 다른 wait50 회차(42~56%)보다 높았다. 외부 영향이 섞였을 수 있지만 확정할 수 없다.
- 예열은 3.2(즉시 거절 방식)에서 효과가 없어 지웠다. 대기 방식에서 예열이 기동 직후 성공률에 영향을 주는지는 측정하지 않았다.

결론: 동시 로그인 2개와 50ms 대기는 정상 부하와 과부하 기준을 모두 통과했다. 기동 직후 로그인 성공률만 98.3~98.5%로, 측정 전에 정한 99%에 미달했다.
