# V2 성능 후속 — 혼합 API 처리 한계의 원인 분리와 개선

V1 기록(`docs/load-test.md` §8, 2026-10-06 KST)에서 관측했지만 원인을 분리하지 못한 320 TPS 실패를 재현하고, 원인을 통제 실험으로 나눈 뒤, 개선 하나를 같은 조건에서 전후 비교한다. 로컬 Docker 단일 환경이며 운영 트래픽이 아니다.

## 0. 역할 구분

| 누가 | 한 일 |
|---|---|
| AI 코딩 에이전트 | 하네스·분석기·앱 코드 작성, 측정 실행, 원자료 집계, 문서 초안 |
| 본인(지관) | 단계별 계획 승인, 측정 기준·가설 답변, 결과 해석·채택 판단 |

## 1. 1단계 — 재현과 한계 지점

### 1.1 측정 전 설계 (2026-10-19 KST 승인)

- 조건: V1 §8과 같다. Docker VM 4 CPU, 앱 2 CPU·2GiB(heap 512MiB~1GiB), Oracle Free(CPU_COUNT=2), 고정 시드(회원 22,021·상품 2,001·주문 600,000·주문상품 1,499,546), 혼합 상품 70%(검색 10%p 포함)·주문 내역 15%·로그인 10%·주문 생성 5%, constant-arrival-rate, 256 VU, HTTP timeout 5초, 단계마다 30초 워밍업·10초 간격·120초 측정 2회.
- 앱 JAR SHA256 `b295004e1e49691a1a7b0cd0a7fec1daaea0cffca7e5541619d603efe7df4dad`, 이미지 `sha256:9d7ce99ad1bf…`가 V1과 같음을 확인했다(`remake/loadtest/results/v2-environment/`). 시작 시 원본/복제 콘텐츠 해시 4종이 V1 결과와 같다.
- 하네스 변경: `Staircase.ps1`에 `-Stages` 파라미터만 추가(기본값은 기존 목록). `capacity.js`, `Run-Capacity.ps1`, `CapacityProbe.java`, 분석기는 바꾸지 않는다. 포화 시 JMX 표본이 성겨지는 한계도 비교 가능성을 위해 그대로 둔다.
- 중단 기준(V1과 같음): 혼합 p95 >500ms, 업무 오류율 ≥1%, warmup/measured drop >0.
- 1-A 재현(label `v2-repro`): 160, 320 TPS 각 2회.
- 1-B 세분화(label `v2-step`): 200/240/280 TPS 각 2회로 구간을 찾고, 마지막 통과~첫 실패 구간을 10 TPS 간격 각 2회로 좁힌다.

### 1.2 측정 전 확정한 판정 기준

- 재현 판정: 160 TPS p95가 V1 73.52~76.20ms의 ±25% 안, 320 TPS 정상 응답 처리량이 V1 210.89~217.34 TPS의 ±10% 안, 오류가 로그인에 집중, 앱 CPU 2.00코어.
- 한계의 정의: 두 회차 모두 중단 기준을 통과한 최고 TPS. 마지막 통과·첫 실패 구간을 10 TPS 해상도로 함께 적는다.

### 1.3 재현 결과 (2026-10-19 KST)

첫 시도(label `v2-repro`)는 160 TPS 2회차가 측정 97초까지 정상(초당 약 160건, 최대 72ms, 앱 1.13코어, CPU 제한 0회)이다가 98초에 앱·Oracle·k6 CPU가 동시에 튀고 관측 표본 간격이 6~14초로 벌어진 뒤, 실행 HTTP 스레드 104개·BCrypt 프레임 스레드 90개까지 쌓여 측정 끝까지 회복하지 못했다(p95 1,716.97ms, 오류 1.064% 중 로그인 196건, drop 501). 앱 내부 변화의 흔적은 없고 VM 단위 교란이 계기였을 가능성이 높으나, VM·호스트 CPU를 수집하지 않아 **계기는 확정하지 못했다.** 이 회차는 "일시 교란 후 회복하지 못하는 붕괴" 사례로 보존한다.

이후 `Run-Capacity.ps1`에 Docker VM 전체 CPU·steal(`/proc/stat`, `vm-stat.txt`)과 Windows 호스트 CPU·상위 프로세스 5개(`host-cpu.txt`) 수집을 추가하고, 분석기에 `vm_and_host_cpu` 집계를 넣었다. 수집 1회에 약 2.7초가 걸려 Docker·Oracle 표본 간격이 늘어난다(JMX 1초 관측은 별도 컨테이너라 영향 없음). 측정 중 호스트에는 `SearchIndexer`, `MsMpEng`, 브라우저 등 백그라운드 부하가 있었고(호스트 CPU 평균 26~35%), VM steal은 모든 표본에서 0이었다. WSL2에서 steal이 보고되지 않을 수 있어 0을 교란 부재의 증거로 쓰지 않는다.

### 1.4 세분화 전 가설 (본인 작성, 2026-10-19 19:35 KST, 1-B 측정 전)

> 한계는 250~260 TPS 정도. CPU 사용량이 늘면 대기시간이 비선형적으로 증가해 p95 500ms 기준을 통과하지 못한다. 그 이상은 2코어 한도 대비 여유가 너무 적어진다.

모든 회차 오류율 0%. `v2-step`은 280에서 중단 기준이 나와 멈췄고, 10 TPS 세분화는 240~280 사이(250·260·270)로 실행했다.

**한계 지점: 270 TPS**(두 회차 통과 최고), 첫 실패 280 TPS(2회 중 1회). 이 환경·혼합·시드·120초×2회 조건의 값이며 일반 용량으로 확장하지 않는다.

- 270 TPS까지 혼합 p95는 61~64ms로 거의 평평했고 앱 CPU만 처리량에 비례해 늘었다(200 TPS 1.35코어 → 270 TPS 1.77코어).
- 270→280 TPS 사이에서 CPU 제한 기간 비율이 4.2~4.7%에서 29.8~37.2%로 급증했고, p95보다 p99와 로그인 p95가 먼저 커졌다. 로그인 외 API p95도 2~3ms에서 12~38ms로 올랐다.
- 280·r2는 측정 78초 무렵 1~2초간 완료가 절반 이하로 떨어진 뒤 대기열이 생겨 약 19초 동안 500ms 이상 응답이 이어졌고 스스로 회복했다. 같은 구간 Hikari awaiting 최대 190. 1.3의 160 TPS 붕괴와 같은 "짧은 정지 → 대기열 누적" 모양이며, 여유 CPU가 남아 회복한 점이 다르다(해석, 원인 분리는 2단계).

원자료 보관: 회차별 k6 원자료 `raw.json.gz`(V2 1단계 18개, 120.6MB)는 저장소 이력을 키우지 않도록 git에서 제외하고 GitHub Release에 첨부한다. 파일별 SHA256과 크기는 `remake/loadtest/results/v2-raw-sha256.txt`에 있으며, 받은 파일을 같은 경로에 두면 `analyze_capacity.py`로 표의 분위수를 다시 계산할 수 있다. 나머지 관측 파일과 분석 JSON은 저장소에 있다.

가설 대조: 한계는 가설(250~260)보다 10~20 TPS 높았다. "CPU 여유가 줄면 지연이 비선형으로 커진다"는 방향은 맞았지만, 지연은 270까지 평평하다가 270~280의 좁은 구간에서 급격히 꺾였다. 기준을 넘긴 직접 원인은 평균 p95가 아니라 짧은 정지 뒤의 대기열(drop)이었다.
