# V2 성능 후속 — 혼합 API 처리 한계의 원인 분리와 개선

V1 기록(`docs/load-test.md` §8, 2026-10-06 KST)에서 관측했지만 원인을 분리하지 못한 320 TPS 실패를 재현하고, 원인을 통제 실험으로 나눈 뒤, 개선 하나를 같은 조건에서 전후 비교한다. 로컬 Docker 단일 환경이며 운영 트래픽이 아니다.

## 0. 역할 구분

| 누가 | 한 일 |
|---|---|
| AI 코딩 에이전트 | 하네스·분석기·앱 코드 작성, 측정 실행, 원자료 집계, 문서 초안 |
| 본인(지관) | 단계별 계획 승인, 측정 기준·가설 답변, 결과 해석·채택 판단 |

## 1. 1단계 — 재현과 한계 지점

### 1.1 측정 전 설계 (2026-10-19 KST 승인)

- 조건: V1 §8과 같다. Docker VM 4 CPU, 앱 2 CPU·2GiB(heap 512MiB~1GiB), Oracle Free(CPU_COUNT=2), 고정 시드(회원 22,021·상품 2,001·주문 600,000·주문상품 1,499,546), 혼합 상품 70%(검색 10%p 포함)·주문 내역 15%·로그인 10%·주문 생성 5%, constant-arrival-rate, 256 VU, HTTP timeout 5초, 단계마다 30초 워밍업·10초 간격·120초 측정 2회.
- 앱 JAR SHA256 `b295004e1e49691a1a7b0cd0a7fec1daaea0cffca7e5541619d603efe7df4dad`, 이미지 `sha256:9d7ce99ad1bf…`가 V1과 같음을 확인했다(`remake/loadtest/results/v2-environment/`). 시작 시 원본/복제 콘텐츠 해시 4종이 V1 결과와 같다.
- 하네스 변경: `Staircase.ps1`에 `-Stages` 파라미터만 추가(기본값은 기존 목록). `capacity.js`, `Run-Capacity.ps1`, `CapacityProbe.java`, 분석기는 바꾸지 않는다. 포화 시 JMX 표본이 성겨지는 한계도 비교 가능성을 위해 그대로 둔다.
- 중단 기준(V1과 같음): 혼합 p95 >500ms, 업무 오류율 ≥1%, warmup/measured drop >0.
- 1-A 재현(label `v2-repro`): 160, 320 TPS 각 2회.
- 1-B 세분화(label `v2-step`): 200/240/280 TPS 각 2회로 구간을 찾고, 마지막 통과~첫 실패 구간을 10 TPS 간격 각 2회로 좁힌다.

### 1.2 측정 전 확정한 판정 기준

- 재현 판정: 160 TPS p95가 V1 73.52~76.20ms의 ±25% 안, 320 TPS 정상 응답 처리량이 V1 210.89~217.34 TPS의 ±10% 안, 오류가 로그인에 집중, 앱 CPU 2.00코어.
- 한계의 정의: 두 회차 모두 중단 기준을 통과한 최고 TPS. 마지막 통과·첫 실패 구간을 10 TPS 해상도로 함께 적는다.

### 1.3 재현 결과 (2026-10-19 KST)

첫 시도(label `v2-repro`)는 160 TPS 2회차가 측정 97초까지 정상(초당 약 160건, 최대 72ms, 앱 1.13코어, CPU 제한 0회)이다가 98초에 앱·Oracle·k6 CPU가 동시에 튀고 관측 표본 간격이 6~14초로 벌어진 뒤, 실행 HTTP 스레드 104개·BCrypt 프레임 스레드 90개까지 쌓여 측정 끝까지 회복하지 못했다(p95 1,716.97ms, 오류 1.064% 중 로그인 196건, drop 501). 앱 내부 변화의 흔적은 없고 VM 단위 교란이 계기였을 가능성이 높으나, VM·호스트 CPU를 수집하지 않아 **계기는 확정하지 못했다.** 이 회차는 "일시 교란 후 회복하지 못하는 붕괴" 사례로 보존한다.

## 2. 원인 분리

### 2.1 측정 전 설계 (2026-10-19 KST, 측정 전 작성)

앱 코드는 바꾸지 않고 하네스와 환경 변수만 바꾼다. 바꾼 항목의 기본값은 1단계와 같다.

- `capacity.js`의 `MIX`: `mixed`(기본, 20칸 혼합), `login`(로그인만), `nologin`(혼합 주기에서 로그인 2칸을 뺀 18칸, 나머지 비율 유지).
- `compose.yaml`의 `POOL_SIZE`(Hikari 최대 풀, 기본 10 = Spring Boot 기본값)와 `JFR_OPTS`. `Restart-App.ps1`이 같은 이미지로 앱 컨테이너를 다시 만들고, 실행 설정은 회차마다 `app-config.txt`에 남긴다.
- JFR: `settings=profile` 기록을 JVM 종료 시 덤프하고(`Collect-Jfr.ps1`), `analyze_jfr.py`가 측정 120초 구간의 `jdk.ExecutionSample`을 분류한다. 이 표본은 Java 코드를 실행 중인 스레드만 잡으므로 Java CPU 시간 비율의 근사이며, GC·JIT·네이티브 시간은 포함하지 않는다.
- 일괄 실행: `Run-V2Isolation.ps1`. 모든 실험은 새로 기동한 앱에서 시작한다. 1단계 회차(장시간 기동된 앱)와의 차이는 30초 워밍업으로 흡수한다고 가정하고, 풀 크기 비교는 풀 10도 같은 방식으로 다시 측정한다.

| 실험 | 조건 | 가설 | 판정에 쓰는 지표 |
|---|---|---|---|
| E1 로그인만 | 20→25→30→35→40 TPS, 각 2회, 중단 기준 동일 | 한계 약 30 TPS(1회 약 65ms CPU × 30 ≈ 2코어) | 한계 TPS, 로그인 1건당 앱 CPU 시간 |
| E2 로그인 제외 혼합 | 243(270의 90%)→480→960 TPS, 각 2회 | 243에서 앱 CPU 0.3코어 이하, 한계는 수백 TPS 이상 | 1건당 CPU 시간, 한계 TPS |
| E3 풀 크기 | 풀 5·10·20 × 혼합 270·300 TPS × 2회, 계단 중단 없이 전부 측정 | 한계·지연이 풀 크기에 거의 무관. 풀 20은 꼬리 지연이 오히려 늘 수 있음 | p95·p99·drop, Hikari awaiting, CPU |
| E4 JFR | 풀 10 × 혼합 270·300 TPS, 각 1회 | Java 실행 표본의 약 85~95%가 BCrypt | 범주별 표본 비율 |

기여도는 E1·E2의 요청 1건당 CPU 시간과 E4의 표본 비율로 계산한다. 1단계의 "BCrypt 스택 표본 비율"(실행 중 HTTP 스레드 스택에 BCrypt 프레임이 있는 비율)은 CPU 점유율이 아니므로 기여도에 쓰지 않는다. Hikari 대기가 원인인지 CPU 포화의 결과인지는 E3로 판정한다. 로그인 하한 20 TPS는 하네스의 최소 도착률 검사(20)를 그대로 둔 결과다.

풀을 키우면 Hikari 대기는 줄지만 300 TPS 오류율은 오히려 늘었다(풀 20이 풀 5의 약 5배). 대기 대신 동시 실행 스레드가 늘어 같은 2코어를 더 잘게 나눠 쓰기 때문으로 해석한다. 270 r2의 p99 차이는 풀 10·20 회차의 측정 첫 30초 지연(아래)에서 나왔다. 풀 5 회차에는 이 구간이 없었지만 풀마다 통과 회차가 하나뿐이라 풀 크기 효과로 판정하지 않는다. Hikari 대기는 원인이 아니라 CPU 포화의 결과다.

**예상 밖 결과: 기동 직후에는 270 TPS를 버티지 못한다.** 새로 기동한 앱의 첫 회차는 풀 크기와 JFR 여부에 관계없이 270 TPS에서 4번 모두 실패했고, 같은 JVM의 두 번째 회차는 3번 모두 통과했다. 실패 회차는 CPU 제한 기간이 100%였고 p95가 측정 내내 회복되지 않았다(풀 10: 10초 구간 p95가 884ms에서 3,009ms로 증가). 통과 회차 중 풀 10·20은 첫 30초 p95가 339~604ms였다가 이후 60~68ms로 안정됐고, 풀 5는 처음부터 62~69ms였다. 1단계는 오래 기동된 앱에서 측정했다. 로그인 1건이 지연 없이 처리되려면 JIT 컴파일이 끝나야 하는데, 여유가 8%뿐인 270 TPS에서는 컴파일 중에 쌓인 대기열을 해소할 CPU가 부족했다고 추정한다(JIT 로그로 확인하지 않음). 따라서 V2 한계 270 TPS는 **충분히 워밍업된 JVM에서만** 성립한다. 3단계 전후 비교는 기동 직후와 워밍업 후 두 상태를 같은 절차로 각각 측정한다.
