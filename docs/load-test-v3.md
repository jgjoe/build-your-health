# BYH V3 — 남은 쿼리·인증·기동 과제

## 0. 범위와 역할

기준은 PR #7 병합 `59439be`이다. AI 에이전트가 설계·구현·측정·분석하고,
사용자는 계획과 정책을 승인하고 결과를 공부한다. 실제 운영 트래픽이나 사용자 직접 구현으로 표현하지 않는다.
작업은 `perf/v3-remake-closure`의 별도 worktree에서 한다. 기존 V2 작업 트리의 미추적 파일은 보존한다.
로컬 커밋만 승인되었고 push·PR·병합·Release 업로드는 승인되지 않았다.

BCrypt cost 10, 기존 데이터 시드 `20261002`, 보안 강도와 실패 판정은 유지한다.
원자료는 git에서 제외하고 SHA256·상대 경로·크기를 남긴다. 실제 관측하지 않은 숫자는 결과로 쓰지 않는다.
실행 전 설계를 먼저 쓰며 결과와 사후 변경은 별도 절에 적는다.

## 1. 주문 내역 — 측정 전 등록

### 가설과 비교

heavy 회원의 선택도 추정(9,734 대 실제 10,000)은 대체로 맞는다.
인덱스 유무보다 행 수 제한 변환/비용 계산이 조기 종료를 놓치는지 확인한다.
`PEEKED_BINDS`에 OFFSET/FETCH가 없다는 사실만으로 원인을 확정하지 않는다.

같은 S2b 인덱스 아래 앱 매퍼 SQL을 MyBatis로 읽고, 그 SQL의 행 제한 부분만 바꾼다.

| 변형 | 목적 |
|---|---|
| CURRENT | 실제 앱 SQL, 최종 적용 후에도 직접 측정 |
| BOUND | OFFSET/FETCH 모두 바인드인 V2 기준 형태 |
| LITERAL_OFFSET | offset 0만 상수 |
| LITERAL_SIZE | size 10만 상수 |
| LITERAL_BOTH | offset 0·size 10 모두 상수 |
| FIRST_ROWS | 바인드 유지, 내부 주문 선택 블록에 FIRST_ROWS(10) |
| ROWNUM | 정렬된 내부 뷰에 ROWNUM 상한, 회원·상한 바인드 |

키셋은 다음 페이지의 건너뛰기 비용을 줄이지만 커서 없는 첫 페이지가 자동 개선되는 것은 아니다.
위 호환 가능한 변형으로 해결되면 페이지 API를 키셋으로 교체하지 않는다.
번호 페이지·size 1~100·total·회원 격리·주문을 먼저 자른 뒤 라인 조인하는 계약을 유지한다.
정렬 키는 ORDER_DATE DESC, ORDER_ID DESC이다. 자유 문자열 SQL 보간은 쓰지 않는다.

### 프로토콜

- 대상: 기존 BYH_PERF 측정 스키마. BYH_LOAD 앱 스키마의 인덱스를 제거하지 않는다.
- 고정 시드 회원 22,021·상품 2,001·주문 600,000·주문상품 1,499,546행.
- S2b: ORDER_ITEMS(ORDER_ID), ORDERS(USER_ID, ORDER_DATE, ORDER_ID). 다른 인덱스 후보는 재탐색하지 않는다.
- heavy u000001, mid u000021, light u002021. offset 0·size 10.
- JDBC fetch size 100, 웜 캐시, 케이스별 예열 5회·측정 30회, 전체 2회.
- 측정 커서 TYPICAL +PEEKED_BINDS, 별도 ALLSTATS LAST +PEEKED_BINDS. 두 plan hash 차이도 기록.
- V$SQL 실행 수 차이로 buffer gets·DB elapsed·처리 행 수를 정규화한다.
- 변형별·회원별 커서를 분리하고 SQL 텍스트, 환경, 자식 커서, 결과 동등성을 보존한다.
- Q2 전 등급과 Q3 mid도 같은 세션에서 측정하여 회귀 기준선을 남긴다.
- 모든 변형의 전체 반환 컬럼·라인은 CURRENT와 비교한다. 라인 간 비지정 순서는 정규화하되
  부모 주문 순서는 그대로 비교한다. 측정 중 결과를 잘라서 fetch하지 않는다.

### 채택 기준

heavy 첫 페이지에서 실제 ORDERS 접근/조기 종료와 실행당 논리 읽기의 개선을 두 회차 확인한다.
응답시간만 줄거나 INDEX 힌트로 경로만 바뀌는 것은 충분하지 않다.
회원별 결과·페이지 계약이 같고 mid/light·Q2/Q3에 실질적 회귀가 없는 가장 작은 수정을 고른다.
개선 배수는 사전에 정하지 않는다. 실험 간 작은 시간 차이를 순위로 과장하지 않는다.

### 실행

`remake/`에서 기존 perf 환경 변수를 설정한 뒤:

```text
sh mvnw -q -Pperf test-compile exec:java -Dexec.args="v3-orders v3-orders-r1"
sh mvnw -q -Pperf test-compile exec:java -Dexec.args="v3-orders v3-orders-r2"
```

인덱스는 위 두 개가 준비되어 있어야 하며 이 명령은 인덱스 DDL을 하지 않는다.
원자료 `remake/perf/results/v3-orders-*/raw.csv`는 제외하고 요약·실제 계획·환경·SQL만 공개한다.

### 1.1 후보 실험 결과

`remake/perf/results/v3-orders-r1/`, `v3-orders-r2/`를 같은 JVM/JDBC·DB 조건으로 실행했다.
초기 실행은 호스트에 `sh`가 없어 측정 전에 실패했다. 저장소의 Windows wrapper
`mvnw.cmd`로 실행했고 두 회차 모두 정상 종료했다. 인덱스는 BYH_PERF에 두 개만 추가했다.

| 변형 | heavy buffer gets (두 회차 동일) | heavy 중앙값 r1 / r2 (ms) |
|---|---:|---:|
| CURRENT (V2 앱) | 8,113 | 32.041 / 30.908 |
| BOUND | 8,113 | 30.534 / 30.168 |
| LITERAL_OFFSET | 8,113 | 30.366 / 29.408 |
| LITERAL_SIZE | 8,113 | 29.527 / 29.725 |
| LITERAL_BOTH | 8,113 | 32.932 / 28.352 |
| FIRST_ROWS | 14,363 | 141.681 / 141.219 |
| ROWNUM | 55 | 0.994 / 0.948 |

모든 변형·등급에서 전체 결과 동등성을 통과했다.
ROWNUM의 mid/light gets는 기존과 같은 67/47이고 Q2는 heavy/mid/light 47/4/3, Q3는 14였다.
FIRST_ROWS(10)은 이 블록에서 주문상품까지 전체 스캔으로 바뀌어 악화했다. 채택하지 않는다.

**원인 분리:** 상수 0/10을 주면 상위 VIEW 추정은 10이 되지만 하위에는
WINDOW SORT PUSHED RANK·ORDERS FULL(추정 9,734)이 남는다. 따라서 단순히
"바인드를 못 봤기 때문"만으로 설명할 수 없다. 정렬된 뷰 바깥 ROWNUM 상한은
COUNT STOPKEY·INDEX RANGE SCAN DESCENDING으로 바뀌고 인덱스와 테이블에서 실제 10건만 읽는다.
비용은 상수 OFFSET/FETCH의 2,428에서 ROWNUM의 50으로 달랐다.
관측 가능한 원인은 이 SQL 형태에서 top-N의 조기 종료/비용 경로가 달라지는 것이다.
Oracle 내부 버그나 특정 숨김 파라미터의 원인이라고 확대하지 않는다.

**선택:** 첫 페이지에 바인드 ROWNUM 상한을 적용한다. 나머지 번호 페이지는 기존
OFFSET/FETCH를 유지하고 공통 정렬 SELECT는 XML 조각으로 공유한다.
상수 SQL 분기·힌트·추가 인덱스·키셋 API 변경이 필요 없다.
다음 `v3-orders-final-r1/r2`는 이 실제 앱 SQL을 CURRENT로 다시 측정한다.
기준은 위 채택 기준 그대로이며 회귀 검사에는 동일 timestamp, 모든 size 경계,
빈 결과, 큰 page, 전체 라인·회원 격리를 추가한다.

### 1.2 실제 앱 반영 후 확인

최종 두 회차 `v3-orders-final-r1/r2`의 CURRENT는 실제 변경된 매퍼다.

| Q1 등급 | V2 CURRENT gets | V3 CURRENT gets | V2 중앙값 r1 / r2 (ms) | V3 중앙값 r1 / r2 (ms) |
|---|---:|---:|---:|---:|
| heavy | 8,113 | 55 | 32.041 / 30.908 | 1.575 / 1.484 |
| mid | 67 | 67 | 1.269 / 1.274 | 1.221 / 1.244 |
| light | 47 | 47 | 1.136 / 1.154 | 1.114 / 1.215 |

heavy의 논리 읽기는 99.32% 감소했다. 측정 범위는 이 고정 데이터의 주문 내역 첫 페이지 SQL이다.
플랜은 2322670658 → 1212016781, ORDERS FULL → INDEX RANGE SCAN DESCENDING,
COUNT STOPKEY에서 실제 10건으로 종료했다. 조인 후에는 주문 10건의 라인 23행을 모두 반환했다.
최종 측정/ALLSTATS plan hash는 모든 CURRENT·등급에서 일치했다.
Q2 gets 47/4/3, Q3 gets 14는 그대로였다. mid/light의 서브 밀리초 차이에 의미를 부여하지 않는다.

`mvnw.cmd verify`: **65 tests, failures 0, errors 0, skipped 0**, JAR 패키징 성공.
실제 Oracle 테스트에 타임스탬프 동률, size 1/2/10/11/100, 마지막/빈/큰 페이지,
잘못된 입력, 주문 전체 라인, 회원 격리, 모든 실험 변형의 독립 조회 대조를 포함했다.
초기 `sh` 부재는 Windows wrapper로 복구했으며 실패한 실행을 성공 회차로 세지 않았다.

측정 후 `checksum`의 행 수/내용 해시는 보존된 V2 SOURCE 값 네 종류와 모두 같았다:
MEMBER 47113733595704, PRODUCT 4283317470972, ORDERS 1291112915996372,
ORDER_ITEMS 3221692166595924. 해당 출력은 최종 r2의 `seed-checksum.txt`에 있다.
원자료 4개는 git 제외, SHA256·크기는 `remake/loadtest/results/v3-raw-sha256.txt`에 있다.

**판정:** 첫 페이지 과제 해결. 깊은 번호 페이지의 OFFSET 비용은 변경하지 않았으며
운영 전체 성능이나 전체 페이지의 개선으로 표현하지 않는다.

## 2. 인증 시간 차이 — 구현 전 원칙

없는 회원도 유효한 cost 10 dummy hash로 정확히 한 번 검증한다.
dummy 해시는 요청마다 생성하지 않는다. 회원이 없으면 dummy 비교 결과와 무관하게 401이다.
문구·상태·세션 불변 계약을 유지하고 검증은 전역 LoginGate 안에서 실행한다.
### 2.1 측정 전 등록

기준 이미지는 검증된 1번 커밋 eaf35db에서 만든 `byh-loadtest-app:v3-before-timing`,
후 이미지는 dummy 검증만 추가한 `byh-loadtest-app:v3-after-timing`이다.
두 이미지 모두 기존 production Dockerfile로 Java 17에서 빌드한다. 동시 2개·대기 50ms,
앱 2 CPU·2GiB·풀 10·같은 BYH_LOAD 시드·HTTP timeout 5초를 유지한다.

- 각 이미지를 새 JVM으로 띄운 뒤 100쌍(200 HTTP 요청)을 버리고 측정한다.
- 알려진 ID의 틀린 비밀번호와 같은 길이의 없는 ID를 1쌍으로 한다.
  알려진 ID는 u000001~u001000, 없는 ID는 u900001~u901000이다.
  비밀번호는 두 경우 모두 동일한 틀린 문자열이다.
- 이미지별 1,000쌍 × 2블록, 블록 사이 10초. 고정 난수로 쌍 순서와 쌍 안 순서를 섞는다.
- Python 표준 HTTP 클라이언트 한 연결에서 순차 요청한다. 동시 요청·재시도는 없다.
  전역 제한 포화를 피하고 각 ID의 실패는 블록마다 한 번이므로 이후 계정 제한 실험과도 구분된다.
- 클라이언트 perf_counter_ns로 요청 전부터 본문 수신 완료까지 잰다.
  모든 응답은 동일한 401 JSON이고 세션 쿠키 발급이 없어야 한다. 예외/429는 성공 표본으로 바꾸지 않는다.
- 원자료에는 블록·쌍·요청 순서·종류·시간·상태만 남기고 실제 요청 비밀번호나 쿠키는 남기지 않는다.
- 블록별 알려진/없는 ID의 중앙값·nearest-rank p95·쌍별 중앙 차이를 보고한다.
  쌍 단위 bootstrap 2,000회(고정 시드)의 중앙값 차이 비율 95% 구간을 계산한다.
- 제안한 동등성 마진 ±10%를 채택한다: **후 이미지 각 블록**의
  (없는 ID 중앙값 − 알려진 ID 중앙값) / 알려진 ID 중앙값의 95% 구간 전체가 ±10% 안이면 통과.
  결과가 불확실하면 불확실하다고 적으며 HTTP가 수학적 constant-time이라고 주장하지 않는다.

경로 검증은 단위 테스트로 두 경우 정확히 한 번의 matches, dummy 일치여도 없는 ID 실패,
dummy hash의 요청별 재생성 없음, 실패 시 세션 미변경을 확인한다.
전체 회귀는 기존 Windows wrapper `mvnw.cmd verify`로 수행한다.

### 2.2 결과

두 이미지에서 각 4,000건의 측정 요청(각 종류 2,000건), 예열 200건을 실행했다.
예상 밖 응답/429/세션 쿠키 발급은 0건이었다.

| 블록 | 전: 존재 / 없음 중앙값 (ms) | 후: 존재 / 없음 중앙값 (ms) | 후 상대 차이 bootstrap 95% 구간 |
|---|---:|---:|---:|
| 1 | 62.433 / 1.820 | 61.198 / 61.128 | −0.360% ~ +0.103% |
| 2 | 61.842 / 1.565 | 60.515 / 60.619 | −0.139% ~ +0.419% |

두 후 블록 모두 사전 ±10% 구간 기준을 통과했다. 후 p95는 존재/없음 각각
63.962/64.392ms(블록 1), 64.309/63.959ms(블록 2)였다.
근거는 `remake/loadtest/results/v3-timing-before/summary.json`,
`remake/loadtest/results/v3-timing-after/summary.json`과 각 이미지 ID·환경이다.
원자료 CSV 두 개는 git에서 제외하고 공통 SHA256 목록에 추가했다.

없는 ID도 encoder.matches 한 번을 실행하고, dummy가 일치하더라도 회원 없음으로 거절한다.
dummy hash는 컨트롤러 생성 때 cost 10으로 한 번 생성한다(기동 때 해시 생성 1회 추가).
일반 실패의 401·문구·세션 ���변과 전역 거절의 DB/BCrypt 미실행은 유지했다.
검증·실제 Oracle 회귀와 Java 17 production 이미지 빌드 모두 성공했다.

**판정:** BCrypt 생략으로 생기던 큰 시간 차이는 제거했다.
HTTP 전체의 수학적 constant-time이나 모든 통계적 계정 열거 공격의 불가능성을 보장하지는 않는다.
이후 계정 잠금에 따른 조기 거절은 존재/없는 ID에 동일한 정책·이력을 적용해야 한다.

## 3. 계정별 보호 — 승인된 정책

5분 내 인증 실패 5회 뒤 60초 잠금, 성공 시 초기화한다.
Oracle에 상태를 보존하고 없는 ID도 같은 정책을 따른다. ID 동일성은 기존 조회와 같다.
잠금 중 요청은 잠금을 무한 연장하지 않는다. 전역 과부하 거절은 인증 실패로 세지 않는다.
전역 Gate → 계정 잠금 확인 → 조회·BCrypt → 원자적 결과 반영 → 성공 세션 순서이다.
BCrypt 중 DB 커넥션/행 잠금을 유지하지 않는다.
잠금 전 이미 입장한 요청은 끝날 수 있으므로 동시 2개에서 최대 한 요청의 추가 실패가 가능하다.
완료 순서로 성공 초기화와 실패 반영을 직렬화한다. 잠긴 계정은 일반 429와 남은 초 Retry-After,
전역 포화는 기존 429·Retry-After: 1을 유지한다.

## 4. 기동 직후 — 구현 전 원칙
